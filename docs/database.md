# MicroCrew Database Design

## Overview
Production database is **Supabase PostgreSQL**. Schema source of truth is `supabase/migrations/*.sql`. Backend uses `validate` mode, never `create` or `update`.

## Auth Schema (Supabase Managed)

### auth.users
Managed by Supabase Auth. Do not modify directly.

Key columns:
- `id UUID PRIMARY KEY` - User identity, used as FK in app tables
- `email TEXT`
- `encrypted_password`
- `email_confirmed_at`
- `created_at`, `updated_at`
- `raw_user_meta_data JSONB` - contains display_name etc.

Our backend never duplicates password - Supabase Auth owns it.

## Public Schema (Application)

### app_user

Foundational profile table.

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
auth_user_id UUID NOT NULL UNIQUE REFERENCES auth.users(id) ON DELETE CASCADE
display_name TEXT NOT NULL CHECK (2-100 chars)
bio TEXT CHECK (<=1000)
college TEXT CHECK (<=200)
course TEXT CHECK (<=200)
year_of_study INTEGER CHECK (1-10)
experience_level TEXT CHECK (BEGINNER, INTERMEDIATE, ADVANCED, EXPERT)
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

- `auth_user_id` UNIQUE ensures 1:1 mapping to auth.users
- Foreign key CASCADE: if auth user deleted, profile deleted
- `updated_at` auto-updated via trigger
- Indexes on `auth_user_id` and `display_name`

Purpose: Store application profile, not auth credentials.

### user_skill

User skills with levels.

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
user_id BIGINT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE
skill_name TEXT NOT NULL CHECK (1-100)
skill_level ENUM('BEGINNER','INTERMEDIATE','ADVANCED','EXPERT')
created_at TIMESTAMPTZ DEFAULT NOW()
UNIQUE(user_id, skill_name)
```

- `UNIQUE(user_id, skill_name)` prevents duplicate skill per user - enforced at DB level
- CASCADE delete: if user deleted, skills deleted
- Indexes on `user_id` and `skill_name` for lookup

Skill levels:
- BEGINNER
- INTERMEDIATE
- ADVANCED
- EXPERT

Future tables (planned, not yet implemented):

## Foreign Keys & Constraints

All business invariants enforced via DB constraints, not just application logic:

- `app_user.auth_user_id` UNIQUE + FK -> prevents duplicate profiles, ensures identity integrity
- `user_skill.user_id` FK + `UNIQUE(user_id, skill_name)` -> prevents orphan skills and duplicates
- CHECK constraints on text lengths and enums -> prevents invalid data even if backend validation bypassed

## RLS (Row Level Security)

Enabled on:
- `app_user`
- `user_skill`

Policies:

**app_user:**
- `SELECT`: authenticated can read all (for teammate discovery, public profiles)
- `INSERT`: only own `auth.uid() = auth_user_id`
- `UPDATE`: only own
- `DELETE`: only own

**user_skill:**
- `SELECT`: authenticated can read all
- `INSERT`: only if owner via `EXISTS (SELECT 1 FROM app_user WHERE app_user.id = user_skill.user_id AND auth_user_id = auth.uid())`
- `UPDATE`/`DELETE`: same ownership check

Why RLS?
- Defense-in-depth
- If frontend ever queries Supabase directly (not via backend), still secure
- Backend uses `service_role` key which bypasses RLS, but service layer still enforces authorization

Important: RLS is NOT replacement for backend authorization. Both layers exist.

## Migrations

Location: `supabase/migrations/`

Naming: `YYYYMMDDHHMMSS_description.sql`

First two:
- `20250919000001_create_app_user.sql`
- `20250919000002_create_user_skill.sql`

Execution:
- Local: `supabase db reset` or `supabase migration up`
- Production: `supabase db push` or via dashboard SQL editor

Never use Hibernate `ddl-auto=create/update` in production. Use `validate`.

## Idempotency & Concurrency

- Profile creation uses `ON CONFLICT (auth_user_id) DO NOTHING` or check-then-create with unique constraint handling - safe for retries
- Skill creation relies on `UNIQUE(user_id, skill_name)` - concurrent duplicate inserts will cause 409, handled gracefully
- All multi-write operations should be `@Transactional`

## Seeding

`supabase/seed.sql` is empty for foundation - no fake users per project rules.

## Backup & Audit

- Supabase provides PITR
- Future: `audit_log` table append-only for tracking changes
- `contribution` ledger will be append-only

## Connection

Backend connects via JDBC:
- `DATABASE_URL=jdbc:postgresql://db.<project>.supabase.co:5432/postgres`
- Use pooling (Supabase pooler) for serverless: port 6543 with pgbouncer

Frontend never connects directly to DB via JDBC - only via Supabase client with RLS (and only for auth currently, data via backend API).
